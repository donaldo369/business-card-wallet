# 만난 정보(날짜·행사·메모) 기록과 HubSpot 일괄 전송 설계

- 작성일: 2026-10-26
- 상태: 초안 (사용자 검토 대기)

## 목적

명함을 받은 맥락, 즉 **언제, 어떤 자리에서 만났는지와 그때 메모**를 명함과 함께 남기고 HubSpot 연락처에도 반영한다.

사용자는 두 가지 상황에서 명함을 등록한다.

- **전시회**: 한 행사에서 수십 장을 받아 오고, 이 명함들을 HubSpot에서 **행사명으로 걸러 세그먼트**를 만든다. 가장 큰 동기다. (최근 전시회 명함 묶음이 아직 스캔되지 않은 채 대기 중이다.)
- **고객 미팅**: 한 미팅에서 보통 **여러 장**(실무자, 결정권자 등)을 받고, 그날이나 며칠 뒤에 스캔한다. 그래서 만난 날짜는 스캔한 날과 다를 수 있다.

두 상황 모두 "한 번에 받은 명함 묶음에 같은 만난 정보를 붙이는" 같은 흐름으로 다룬다. 전시회는 행사명을 채우고, 미팅은 행사명을 비운 채 날짜와 메모만 쓴다.

## 목표

1. 스캔 직후 화면에서 묶음 전체에 **만난 날짜 / 행사명(선택) / 공통 메모(선택)**를 한 번 입력한다.
2. 같은 화면에서 **명함마다 사람별 메모**를 적을 수 있다. 예: "결정권자, 예산 3월 확정"
3. 저장할 때 **HubSpot으로 한 번에 전송**한다. 한 장을 저장할 때도 마찬가지다. 단, HubSpot에 올리지 않는 명함(개인 명함 등)도 있으므로 **명함마다 보낼지 고를 수 있다**.
4. HubSpot에서 "참석 행사에 'OO' 포함"으로 세그먼트를 만들 수 있다. 같은 사람이 여러 행사에 오면 **모든 행사에 속해야 한다** (덮어쓰기 금지).
5. 앱의 명함 상세 화면에서 그 사람과의 **만남 기록**을 날짜순으로 볼 수 있다.

## 하지 않는 것

- 이미 저장된 명함 여러 장을 골라 행사명을 한꺼번에 붙이는 기능. 대기 중인 전시회 명함은 새 흐름으로 처음부터 스캔한다.
- 기존 **그룹** 기능 변경. 그룹은 원래 용도(개인/업무 명함 구분)로 그대로 두고, 행사와 연결하지 않으며 HubSpot에도 보내지 않는다.

## 실패로 보는 경우 (기술적으로 동작해도)

- 같은 행사가 표기만 다르게 들어가 HubSpot 세그먼트가 갈라지는 경우. 예: "2026 교육박람회"와 "교육박람회 2026"
- 재방문자를 다시 등록했더니 이전 행사가 HubSpot에서 사라지는 경우
- 수십 장을 등록한 뒤 HubSpot 전송을 위해 한 장씩 눌러야 하는 경우
- HubSpot 전송 일부가 실패했는데 앱 저장까지 날아가거나, 어떤 명함이 실패했는지 알 수 없는 경우

## 사용자가 정한 화면 (목업으로 확인함)

### 1. 여러 장 스캔 결과 화면 (`BatchResults`) — 전시회와 미팅 공통

목록 **맨 위**에 "🤝 만난 정보 · N명 모두" 박스를 둔다. 행사 정보는 스캔한 **다음** 이 화면에서 입력한다. 스캔 전에 묻거나 "행사 모드"를 켜 두는 방식은 쓰지 않는다.

- **만난 날짜**: `오늘 / 어제 / 그제 / 📅 날짜 선택` 버튼. 기본값은 오늘이다.
- **행사명 (선택)**: 직접 입력한다. 입력란 아래에 **최근에 쓴 행사명을 추천**으로 띄워서 탭 한 번에 똑같이 넣을 수 있게 한다. 표기 불일치를 막는 핵심 장치다.
- **공통 메모 (선택)**: 한 줄 이상 입력할 수 있는 칸.

그 아래 명함 목록에서는 각 명함 행 바로 밑에 **사람별 메모 칸이 항상 보인다**. 누를 때만 펼치는 방식은 쓰지 않는다.

**HubSpot에도 보내기 스위치**
- 만난 정보 박스 안에 "HubSpot에도 보내기" 스위치를 두고, **기본값은 켜짐**이다. 끄면 묶음 전체를 앱에만 저장한다.
- 명함 행마다 같은 스위치(체크)가 있어 **한 장씩 뺄 수 있다**. 예: 전시회 명함 24장 중 2장 제외. 위쪽 스위치를 바꾸면 모든 행에 적용되고, 그다음 행별로 조정한다.

하단 버튼: 보낼 명함이 있으면 **"N장 저장 + M장 HubSpot 전송"**, 없으면 **"N장 저장"**.

### 2. 한 장 스캔 후 편집 화면 (`CardEditForm`, 신규 등록일 때)

명함 사진 **바로 아래, 이름 칸보다 위**에 같은 "🤝 만난 정보" 박스를 **항상 펼쳐서** 둔다. 구성은 날짜 버튼, 행사명(선택, 추천 포함), 메모(선택), **"HubSpot에도 보내기" 스위치(기본 켜짐)**다. 한 장이라 공통 메모와 사람별 메모를 나누지 않고 메모 칸 하나만 둔다.

스위치가 켜져 있으면 저장 버튼은 "저장 + HubSpot 전송"이 되고, 저장한 뒤 바로 HubSpot으로 보낸다. 지금은 한 장을 저장해도 HubSpot으로 가지 않고 상세 화면에서 따로 눌러야 하는데, 이 동작을 바꾸는 것이다.

## HubSpot 쪽 동작

| 정보 | HubSpot에 들어가는 곳 | 규칙 |
|---|---|---|
| 행사명 | 연락처 칸 **"참석 행사"** (여러 개 체크 가능한 형식) | 기존 값에 **추가만** 한다. 행사명이 비어 있으면 건드리지 않는다. |
| 만난 날짜 | 연락처 칸 **"최근 만난 날짜"** (날짜) | 기존 값보다 최근일 때만 갱신한다. |
| 메모 | 연락처 **활동 기록(타임라인)의 노트** | 만남 1건마다 노트 1개. 날짜, 행사명, 공통 메모, 사람별 메모를 합쳐서 남긴다. |

노트 예시:

```
2026.10.26 · 한빛교육 본사 미팅, 견적 요청
결정권자, 예산 3월 확정
```

- 처음 보는 행사명이면 앱이 HubSpot "참석 행사" 칸에 그 항목을 **자동으로 추가**한 뒤 체크한다.
- 위 동작에 필요한 HubSpot 비공개 앱 토큰 권한(연락처 칸 설정 변경, 노트 작성 등)이 없으면, 기존 구독 오류처럼 **어떤 권한을 추가해야 하는지 알려 주는 문구**를 보여 준다.
- 연락처 저장, 이메일 구독 처리(PR #2), 행사·날짜·노트 반영은 기존 패턴대로 **연락처 저장이 성공해야 나머지를 진행**하고, 부가 작업이 실패해도 연락처 저장은 되돌리지 않는다.
- 기존 `/api/hubspot` 동작(이메일이 있으면 세 가지 구독을 켜는 것 포함)은 일괄 전송에도 그대로 적용된다.

## 앱 안의 데이터와 화면

- 만남 기록은 명함 한 장에 **여러 건** 쌓인다. 같은 사람을 다시 만나 스캔하면 기존 중복 처리(이름 + 휴대폰 번호로 같은 사람 판단 → 최신 정보로 덮어쓰고 이전 값은 history에 보관)를 그대로 따르고, 만남 기록은 **기존 명함에 1건 추가**한다.
- 만남 1건에 저장할 내용: 만난 날짜, 행사명(없을 수 있음), 공통 메모, 사람별 메모, HubSpot 반영 여부.
- 명함 상세 화면(`CardDetail`)에 **"만남 기록"** 섹션을 두고 최근 날짜부터 보여 준다.
- 행사명 추천 목록은 사용자의 기존 만남 기록에 있는 행사명에서 만든다. 최근에 쓴 순서로 보여 준다. 현재 앱 사용자는 한 명뿐이라 HubSpot에 이미 있는 행사명까지 가져올 필요는 없다.
- DB 변경은 `supabase_setup.sql`에 추가하고, 기존 테이블처럼 **RLS로 본인 데이터만** 읽고 쓰게 한다.

## 일괄 전송 흐름과 실패 처리

1. 저장 버튼을 누르면 **앱 저장을 먼저** 끝낸다(스위치를 끈 명함 포함). 명함과 만남 기록이 저장된다.
2. 이어서 스위치가 켜진 명함만 HubSpot 전송을 진행하고, 진행 상황을 보여 준다(예: 12/24). 기존 일괄 스캔의 진행 표시와 비슷하게 한다.
3. 끝나면 결과를 요약해서 알려 준다: 성공 N건, 실패 M건과 실패한 이름·이유.
4. 실패한 명함은 앱에 저장된 채로 남는다. 상세 화면의 기존 HubSpot 버튼으로 **다시 보낼 수 있고**, 이때 아직 HubSpot에 반영되지 않은 만남 기록(행사·날짜·노트)도 함께 보낸다.
5. 스위치를 끄고 저장한 명함도 나중에 상세 화면의 기존 HubSpot 버튼으로 보낼 수 있고, 이때 그 명함의 만남 기록도 함께 반영된다.
6. HubSpot 토큰이 설정되지 않았으면 스위치를 숨기고 버튼은 "N장 저장"으로만 동작한다.

## 제약

- Next.js 16.4 App Router 프로젝트다. `AGENTS.md`에 따라 코드를 쓰기 전에 `node_modules/next/dist/docs/`의 관련 문서를 확인한다.
- HubSpot 일괄(batch) 구독 API는 Enterprise 전용이라 지금 코드는 단건 호출을 쓴다. 다른 HubSpot 호출도 플랜 제약을 확인하고, 수십 건을 보낼 때 **HubSpot 호출 횟수 제한**에 걸리지 않게 한다.
- Vercel 함수의 요청/응답 크기는 4.5MB로 제한된다. 이미지는 이미 Supabase Storage에 올라가 있으므로 HubSpot 전송 요청에는 텍스트만 담는다.

## 설계자의 판단으로 정한 것 (사용자 확인 전)

- HubSpot "최근 만난 날짜"는 칸 하나에 최신 날짜만 두고, 날짜별 기록은 노트로 남긴다.
- 공통 메모와 사람별 메모는 HubSpot 노트 하나로 합친다.
- 한 장 편집 화면에서는 메모 칸을 하나만 둔다.
- 저장된 명함을 **수정**하는 화면(기존 명함 편집)에는 만난 정보 박스를 넣지 않는다. 만난 정보는 새로 스캔할 때만 입력한다.
- 여러 장 스캔 결과에서 명함 하나를 눌러 인식 결과를 고치면, 편집 화면은 **필드만 고치고 결과 목록으로 돌아간다**. 이때 만난 정보 박스는 보이지 않는다. 그 명함은 따로 저장되지 않고, 나머지 명함과 함께 묶음의 만난 정보와 자기 사람별 메모를 달고 "N장 저장 + HubSpot 전송"으로 저장·전송된다. 지금은 따로 저장되고 목록에서 빠지는데, 그러면 행사명이 빠지거나 HubSpot 전송이 누락되므로 바꾼다.
- 행사명과 메모가 모두 비어 있어도 만남 기록은 만든다(날짜만 있는 기록). HubSpot "최근 만난 날짜"는 갱신하지만, **적을 내용이 없는 노트는 만들지 않는다**.
- HubSpot 반영 여부는 만남 기록마다 **항목별로 따로** 기록한다(참석 행사 / 최근 만난 날짜 / 노트). 다시 보낼 때는 실패한 항목만 보내서 노트가 중복되지 않게 한다. 결과 요약에서는 연락처 저장이 성공하고 일부 항목만 실패한 경우를 "부분 성공"으로 따로 보여 주고, 실패한 항목과 이유를 함께 알려 준다.

## 구현하는 사람이 정할 것

- 만남 기록의 테이블 구조, 컬럼 이름, 인덱스
- HubSpot 칸의 내부 이름과 만드는 방법(앱이 없으면 생성할지, 1회 설정 스크립트로 만들지)
- HubSpot 전송을 브라우저에서 한 건씩 반복 호출할지, 서버 라우트 하나에서 묶어 처리할지 (호출 횟수 제한과 함수 실행 시간 고려)
- 날짜 선택 UI의 세부 모양. 기존 화면 스타일(글래스, 보라 계열)을 따른다.
- 테스트 범위. 기존 `src/lib/*.test.mjs`처럼 순수 로직(노트 문구 조합, 행사 값 합치기, 날짜 비교 등)은 단위 테스트를 둔다.
